# Baseline sources — where each definition comes from and why it is used

Every condition, timer, event name and action name in `protocols/` cites one of the entries below as `[Bn]`. The rule: a baseline is used only when (1) it is the primary artefact under study, (2) it is a published standard or protocol convention, or (3) it is an oracle from a peer-reviewed comparable project already in the reading records. For each entry the table states what was actually read (with the cached bytes' SHA-256 so a reviewer can check the same text), why it was chosen over alternatives, and how it is adapted here. Text that could not be read (ISO 21384-3 body, ASTM F3269 body) is marked as such and nothing is claimed from it.

Snapshots live outside git under `~/.cache/uav-failsafe-composition/baselines-2026-09-16/` (and `…/prior-art-closeout/2026-09-15/` for B4, B6). `tests/test_baselines.py` checks that every `[Bn]` cited in `protocols/` and `model/` exists here and that every entry is cited at least once.

## Baselines considered and not used

- **RTCA DO-365 (Detect and Avoid MOPS)** — defines *well clear* for separation. Only the product page was reachable; separation between vehicles is outside the single-vehicle protocol. Revisit for fleet composition (URC-10).
- **ISO 21384-3 §9.4.10 body** — not accessible; only titles and terms are used (B8).
- **ASTM F3269 body** — not accessible; scope plus two public papers are used (B9). If the owner obtains the standard, the U1/U2 wording should be re-checked against its requirement numbers.
- **EASA Easy Access Rules for UAS** — SORA 2.0 as AMC; the JARUS 2.5 main body (B7) is the primary text and was read directly.
