## Where the review needs correcting

**F1 names the symptom, not the cause.** The review treats the injection timestamp discrepancy
(`t_vehicle_s` 57.780 against `detail.t_vehicle_s` 58.128) as evidence that neither field can be declared
ground truth, and proposes representing uncertain instants as intervals. The interval work is right, but the
specific discrepancy has a plain cause. The runner reads the vehicle clock at the moment it injects and logs
that reading. The normaliser then looked for a field named `t`, never found it, fell back to host time minus
the median offset, and pushed the real reading down into `detail`. The measured instant was present in the
capture the whole time and was overwritten by an estimate. Calling both fields equally uncertain would have
preserved the bug under a more careful-sounding description.

So the repair is ordered: use the vehicle's own reading wherever one exists, and reserve interval treatment
for the instants that genuinely have none, which here are the heartbeat, the status texts, and the host
send-stop. That also gives the interval a defensible construction, which the review left open: bracket a
host-only instant by the two nearest real vehicle-clock readings either side of it in host time. Both clocks
advance monotonically, so the true instant lies between them. The offset spread is not used as an uncertainty,
because the review is right that a dispersion is not a calibrated bound.

**F5's U4 speed bound is an error of direction, not only of conservatism.** The review says dividing distance
by a maximum speed "is not a conservative upper bound on completion time". It is the opposite of one. Distance
divided by the greatest attainable speed is the *least* time the manoeuvre could take. Using it as a deadline
makes the property fire on every run that flies at anything less than full speed, which would have produced a
stream of false violations reported as composition defects. `protocols/unsafe-composition-properties.json`
currently derives `expected_manoeuvre_time` this way, so this is a live defect in the property set and not a
presentational point.

**F11 stopped one entry short.** The review found L32 and correctly explained why no identifier check could
catch it: the entry resolved cleanly *and* matched its own recorded title, because the wrong title had been
recorded too. Running that check anyway over all 55 entries found a second, different error. L43 recorded
`Plan-and-Avoid: conflict-aware contingency landing planning`, a paraphrase of the finding rather than a title;
the arXiv record for the same identifier reads `Plan-and-Avoid: Real-Time Aircraft Trajectory Coordination in a
Multi-Agent Environment`. The identifier was right and the title had drifted, which is the mirror image of L32.
One failure mode was invisible to the machine check and the other was invisible to a human reading the register,
so the register now carries both, and `literature/axes.md` is generated rather than maintained by hand.

## Where the review is right and the repository was wrong

**F10's numbers reproduce exactly.** Recomputed here without reference to the review: 57 of 60 gives a
two-sided Wilson 95% interval of 0.8630 to 0.9829; 50 of 50 gives a one-sided exact 95% lower bound of
0.94184; 60 of 60 gives 0.95130. The point stands that neither a 50-case nor a 60-case perfect run licenses a
"95% agreement at 95% confidence" claim, and that deterministic hand-picked offsets are not a Bernoulli sample
whatever the arithmetic says.

**F2's verdict precedence was doing real damage.** The verifier appended identity failures, invalid-run
reasons and behavioural mismatches to one list and then reported `refuted` if the list was non-empty. A
capture from the wrong case, or a run the apparatus had already marked invalid, would have been published as
PX4 contradicting its own hand-derived timeline.

**F3 is the reason "no action was selected" is not yet a claim.** The normaliser wrote `selected_action: null`
into every sample, emitted rising hazard edges only, and read `vehicle_status.failsafe` from the log and threw
it away. PX4's `Action::None` is a value in the enum; not observing the selector is a different fact, and the
representation could not tell them apart. The current claim stays as the review words it: *no recovery
transition or announcement was observed in these development runs; the selector's internal cause is unresolved.*

## What changed in this packet

- `harness/trace.py`: every instant carries `t_source`; injector events keep the vehicle clock reading the
  runner already took; host-only instants carry a bracketing `t_vehicle_interval_s`; hazard flags record both
  edges; `vehicle_status.failsafe` becomes a `failsafe_state` event; flag state at window entry is preserved;
  `selected_action` is the string `unobserved`, never null; the intended mode comes from the case or from the
  mode command in the raw capture, and is null rather than defaulted when neither exists.
- `harness/verify.py`: validity, observability, stimulus and conformance are answered in that order, and only
  conformance can return `refuted`; the comparison uses the response window with the state entering it
  recorded separately; a reconstructed instant whose interval straddles the deadline returns `inconclusive`;
  mode entry and recovery completion are separate fields.
- `harness/run_case.py`: the intended mode is written into `case.json` instead of being patched onto the
  manifest after normalisation, so a re-normalised Auto Loiter run is no longer read as the Offboard case.
- `literature/`: L32 carries the Simplex paper (`doi:10.1109/MS.2001.936213`, Sha, IEEE Software, 2001) with
  the erroneous acquisition preserved under `quarantined_identifier`; L43's title is corrected the same way;
  identity is split from access; `audit_identity.py` checks every identifier against its registry and
  `render_axes.py` generates `axes.md` from the register.
- Entry points no longer say no autopilot has run.

## What is deliberately not done here

F5's property rewrite, F6's model state, F7's witness classification, F8's full result taxonomy, F9's ordered
interaction pilot and F12's comparator all depend on decisions this packet should not make alone, or on an
environment that does not exist yet. They stay as tasks. The U4 speed-bound error above is recorded as a known
defect in the property set rather than patched here, because changing a property's deadline is a protocol
amendment and belongs with the rest of F5.

The oracle (TASK 3) remains the critical path and remains blocked. The review is right that the macOS
sanitizer failure establishes a blocker on that host and not a mathematical need for Linux, and right that
installing anything on the headless GPU host must not become a scientific dependency.
